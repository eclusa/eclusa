From harness/formalize.py:
```python
GHC_CONTAINER_NAME = "ghc-sidecar"
GHC_WORKSPACE = "/workspace"
GHC_TIMEOUT_SECONDS = 10

async def verify_with_ghc(haskell_source: str) -> tuple[bool, str]:
    """Write Haskell to a workspace tempfile and type-check it with GHC.

    The subprocess: docker exec ghc-sidecar ghc -fno-code <tempfile.hs>
    Returns (success: bool, output: str).
    On success: returncode==0, output is stdout+stderr.
    On failure: returncode!=0, output has GHC error messages with temp path normalized to 'constraints.hs'.
    On timeout: returns (False, "GHC compilation timed out").
    """
```

From docker-compose.yml:
```yaml
  ghc:
    image: haskell:9.10.1
    container_name: ghc-sidecar
    command: ["sleep", "infinity"]
    volumes:
      - ghc_workspace:/workspace
    restart: unless-stopped

  executor:
    volumes:
      - ghc_workspace:/workspace  # Shared with ghc sidecar
```

The executor and ghc-sidecar share the `/workspace` volume. `verify_with_ghc` writes a temp .hs file to /workspace (or /tmp if /workspace doesn't exist on host), then calls `docker exec ghc-sidecar ghc -fno-code /workspace/<file>.hs`.

On the host (where tests run), /workspace does not exist, so verify_with_ghc falls back to tempfile.gettempdir() (e.g., /tmp). But the docker exec command still references the host path. This means when running from the HOST, the temp file path is on the host filesystem, not inside the container.

IMPORTANT: verify_with_ghc uses `docker exec ghc-sidecar ghc -fno-code <local_path>` where local_path is on the HOST. The ghc-sidecar container has /workspace mounted but NOT /tmp. So for tests running on the host, we need to ensure the temp file is written to a path that the ghc-sidecar container can see.

Solution: The test should set `harness.formalize.GHC_WORKSPACE` to a directory that maps to /workspace inside the container. Since the docker-compose volume `ghc_workspace` is a named volume (not a bind mount), the host path is managed by Docker. The simplest approach: use monkeypatch to set GHC_WORKSPACE to the resolved host path of the ghc_workspace volume, OR just use /tmp and monkeypatch the docker exec command to copy the file into the container first.

Actually, re-reading verify_with_ghc: it writes to _workspace_dir() which returns /workspace if it exists, else tempfile.gettempdir(). On the host, /workspace likely doesn't exist, so it uses /tmp. Then it calls `docker exec ghc-sidecar ghc -fno-code /tmp/constraints_xxx.hs` -- but /tmp on the host is NOT mounted into ghc-sidecar.

The cleanest fix for E2E testing: monkeypatch `_workspace_dir` to return a path that IS accessible inside the container via a bind mount, or use docker cp to get the file into the container. BUT -- the simplest approach that works: create /workspace on the host (or use a temp dir and monkeypatch). Since the ghc_workspace volume is a named Docker volume, we can find its mountpoint and use that.

SIMPLEST APPROACH: Use `docker cp` to put the file into the container, then exec ghc. But this means we can't use verify_with_ghc directly from the host.

ACTUAL SIMPLEST APPROACH: Create a small wrapper that:
1. Writes the .hs file locally
2. Uses `docker cp <file> ghc-sidecar:/workspace/` to copy it in
3. Runs `docker exec ghc-sidecar ghc -fno-code /workspace/<filename>`
4. Cleans up

This tests the GHC sidecar directly without relying on verify_with_ghc's path assumptions. The test proves SCC-E2E-02 (GHC verification works) rather than testing the specific Python function's path handling.

ALTERNATIVELY: If /workspace happens to work because Docker named volumes can be accessed from the host (they can via `docker volume inspect`), we could use that path. But this is fragile.

BEST APPROACH: Test both paths:
- Test 1: Call verify_with_ghc directly. If the path issue causes GHC to fail with "file not found", monkeypatch GHC_WORKSPACE to use `docker volume inspect` to find the actual host mountpoint.
- Test 2: Direct docker exec test as a fallback if verify_with_ghc path issues arise.

Actually the most pragmatic: just test via docker cp + docker exec directly. This proves the GHC sidecar works (SCC-E2E-02). The verify_with_ghc function is already unit-tested in tests/test_formalize.py.

**Approach:** Use direct `docker exec` + `docker cp` to test the ghc-sidecar container, proving the sidecar itself works. This avoids the path-mapping complexity of verify_with_ghc when running from the host. The verify_with_ghc function is already thoroughly unit-tested in tests/test_formalize.py; this E2E test proves the actual GHC container works.

**Helper function: `run_ghc_check(haskell_source: str) -> tuple[bool, str]`**
1. Write haskell_source to a temp file on host.
2. `docker cp <tempfile> ghc-sidecar:/workspace/check.hs`
3. `docker exec ghc-sidecar ghc -fno-code /workspace/check.hs` via asyncio.create_subprocess_exec
4. Capture stdout+stderr, return (returncode==0, output).
5. Cleanup: `docker exec ghc-sidecar rm -f /workspace/check.hs` and remove local temp file.
6. 10-second timeout on the subprocess.

**Prerequisite check:** Before tests run, verify ghc-sidecar container is running:
```python

    pytest.skip("ghc-sidecar container not running")
```
