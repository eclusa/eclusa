  <files>harness/refine_agent.py</files>
  <action>
Create `harness/refine_agent.py`. This module defines the Refine agent that runs the Build mode conversation.

**Module structure:**

1. `RefineContext` dataclass — holds the asyncpg.Connection and actor_id that tool implementations need. Pass as `deps` to the pydantic-ai Agent.

2. `RefineToolResult` — a Pydantic BaseModel for structured tool output that the agent can interpret. Fields: `tool`, `results: list[dict]`, `summary: str`.

3. Three tool functions decorated with `@agent.tool` (use `RunContext[RefineContext]` as first arg per pydantic-ai tool signature):
   - `search_knowledge(ctx, query: str) -> RefineToolResult`
     - Calls `embed_texts([query], httpx.AsyncClient())` to get the query embedding
     - Calls `hybrid_search(query, embedding, ctx.deps.conn, limit=8)`
     - Returns `RefineToolResult(tool="search_knowledge", results=[r.model_dump() for r in results], summary=f"Found {len(results)} knowledge graph entities")`
     - Gracefully returns empty results if embedding call fails (log warning, don't raise)
   - `search_schemas(ctx, query: str) -> RefineToolResult`
     - Same embedding pattern as search_knowledge
     - Calls `search_schema_commons(query, embedding, ctx.deps.conn, limit=8)`
     - Returns `RefineToolResult(tool="search_schemas", results=[r.model_dump() for r in results], summary=f"Found {len(results)} schema commons matches")`
   - `create_scc_cascade(ctx, scope_doc: str) -> str`
     - Calls `create_scc_cascade_from_refine(ctx.deps.conn, scope_doc, ctx.deps.actor_id)` from `executor.scc` (imported at call time to avoid circular import, or use `from executor.scc import create_scc_cascade_from_refine`)
     - Returns the cascade_id as a string
     - The tool docstring must clearly say: "Call this when you have enough context and the scope is clear. Provide a complete scope document. Returns the cascade ID."

4. System prompt for the agent:
   ```
   You are the Refine agent for Eclusa's software construction pipeline.
   Your job is to help the operator clarify what they want to build.

   You have three tools:
   - search_knowledge: search the organizational knowledge graph for relevant context
   - search_schemas: search the schema commons for matching API specs and type definitions
   - create_scc_cascade: call this when you have enough context to define a clear scope

   Behavior:
   - If the user's message is vague or incomplete, ask clarifying questions. Do not rush to create a cascade.
   - If the user says something like "hi" or "hello", greet them and ask what they want to build.
   - Use search_knowledge and search_schemas to gather relevant context before creating the cascade.
   - When you have: (1) a clear goal, (2) non-goals or constraints, and (3) searched for relevant context — call create_scc_cascade.
   - The scope_doc passed to create_scc_cascade should be a structured document with: Goal, Non-goals, Constraints, Relevant context found, Open questions (if any).
   - After calling create_scc_cascade, tell the user the cascade was created and show the cascade_id.
   ```

5. `build_refine_agent(model: str | None = None) -> Agent[RefineContext, str]`:
   - Returns an `Agent(model or DEFAULT_REFINE_MODEL, system_prompt=REFINE_SYSTEM_PROMPT, deps_type=RefineContext)`
   - `DEFAULT_REFINE_MODEL = os.environ.get("SCC_MODEL_REFINE", os.environ.get("DEFAULT_MODEL", "openai:glm-5.1"))`

Use `from __future__ import annotations`. Import `asyncpg`, `httpx`, `os`, `logging`, `dataclasses.dataclass`. Import `pydantic_ai.Agent`, `pydantic_ai.RunContext`. Import `pydantic.BaseModel`.

Do NOT import from `executor.scc` at module level — import inside `create_scc_cascade` tool body to avoid circular imports (chat_bridge -> scc -> chat_bridge is the risk).

Add `create_build_chat_cascade` function to `adapters/web/chat_bridge.py`. This is the build-mode equivalent of `create_chat_cascade` — it bootstraps the DB records for a build mode session.

**Function signature:**
```python
async def create_build_chat_cascade(
    conn: asyncpg.Connection,
    actor_id: str,
    first_message: Any,
    *,
    model_config: dict | None = None,
) -> dict[str, str]:
```

**Implementation — inside a single `conn.transaction()`:**

1. Create intent (same as chat cascade):
   - `source = 'chat'`
   - `raw = first_message_text`

2. Create cascade with build-mode shape:
   - `shape = {"mode": "build", "title": title}`
   - `narrative = title` (same as chat)
   - `state = 'active'`

3. Create stage:
   - `type = 'narrowing'`
   - `state = 'pending'`  (NOT 'active' — it becomes active when first turn runs)
   - `input = {"mode": "build", "first_message": first_message_text, "scc_stage": "refine"}`

4. Create work_session:
   - `harness_type = 'build'`  (distinguishes from 'chat' sessions for query purposes)
   - `model = DEFAULT_CHAT_MODEL`
   - `state = 'running'`
   - `message_history = '[]'`

5. If model_config is provided, update cascade.model_config (same pattern as create_chat_cascade).

**Returns:** `{"intent_id", "cascade_id", "stage_id", "session_id"}`

Also update `__all__` to include `"create_build_chat_cascade"`.

The function is intentionally a thin DB bootstrap — it does NOT invoke the agent. The agent is invoked per-turn from `chat.py`.
