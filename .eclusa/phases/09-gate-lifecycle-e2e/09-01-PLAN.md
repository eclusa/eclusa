Stage table schema (relevant columns):
```sql
stage.id          UUID PK
stage.cascade_id  UUID FK -> cascade
stage.type        stage_type ENUM ('narrowing', 'gate')
stage.state       stage_state ENUM ('pending', 'active', 'blocked', 'resolved', 'skipped')
stage.depends_on  UUID[]
stage.input       JSONB
stage.resolve_token  TEXT (nullable)
stage.expires_at  TIMESTAMPTZ (nullable)
stage.resolved_at TIMESTAMPTZ (nullable)
stage.resolved_by UUID (nullable)
```

The `dispatch_stage` function routes gate stages to `surface_gate()` which sets the stage to `state='blocked'`. The `claim_ready_stages` query only picks up stages where `state='pending'` AND all depends_on stages are in terminal states (`resolved` or `skipped`). A `blocked` stage is NOT terminal, so downstream stages depending on a blocked gate will NOT be claimed.

To resolve a gate: call `resolve_gate(conn, stage_id, actor_id)` which sets `state='resolved'`, writes a `gate_resolved` ledger entry, and fires `pg_notify` on both `stage_changed` and `stage_changed:{cascade_id}`.
